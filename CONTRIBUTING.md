# Contributing

## Рабочий процесс

Перед началом задачи обновите ветку от основной ветки проекта и проверьте, что изменение не конфликтует с текущими работами. Если ветка заметно отстает от основной, не запускайте массовое форматирование и не применяйте автофиксы по всему `app/`: это увеличивает риск конфликтов.

Держите изменения небольшими и тематическими. В один коммит не стоит смешивать прикладную логику, форматирование, правки типов и изменения tooling.

## Установка окружения

Проект использует `uv` для dev tooling.

```bash
make install-dev
make hooks-install
```

Для зависимостей приложения:

```bash
make install
```

## Проверки

Базовая проверка для обычной разработки:

```bash
make check
```

Она запускает:

```bash
make lint
make test
```

Дополнительные необязательные проверки:

```bash
make lint-docs
make type-check
```

`make lint-docs` проверяет docstring-правила. Не исправляйте docstring-долг массово в задачах, которые не посвящены документации.

`make type-check` запускает `mypy`. Строгая типизация внедряется постепенно, поэтому исправляйте type-check ошибки только в рамках отдельной задачи или в затронутом модуле.

## Форматирование и lint

`ruff` используется для lint и форматирования:

```bash
make lint
make format
```

Не запускайте `make format` по всему проекту в ветке, которая отстает от основной. Для таких веток форматируйте только файлы, которые действительно меняете.

Pre-commit hooks могут применять автофиксы. Если нет задачи менять `.py` файлы, не запускайте hooks вручную на весь проект.

## Тесты

Для текущего набора обязательных тестов:

```bash
make test-critical
```

Новые изменения в бизнес-логике желательно сопровождать точечными тестами. Если тесты не добавлены, укажите причину в описании изменения или pull request.

## Коммиты

Используйте короткие сообщения в стиле Conventional Commits:

```text
feat(scope): add feature
fix(scope): fix behavior
chore(tooling): update checks
docs: update contributing guide
```

Отдельный коммит должен отвечать на один вопрос: что изменилось и зачем. Массовые автофиксы, если они нужны, делайте отдельным коммитом.

## Документация

Документируйте не очевидный код, а правила и контракты, которые трудно восстановить из реализации: бизнес-инварианты, side effects, интеграции, ограничения внешних API и причины нетривиальных решений.

Docstring-долг закрывается постепенно. Не добавляйте пустые или формальные docstring только ради прохождения проверки.

## Миграции базы данных

Схема версионируется Alembic (`migrations/`). Меняете модель — генерируете ревизию (`make migration m="..."`), ревьюите сгенерированный SQL и коммитите его вместе с изменением модели. Смена типа колонки на непустых данных требует ручного `postgresql_using` — autogenerate его не добавляет.

### Изменения типов на боевой БД (например, нормализация дат, миграция `0002`)

Миграция `ALTER ... TYPE ... USING ...` падает целиком, если хотя бы одна строка не подходит под формат. Поэтому перед применением:

1. Сделайте бэкап: `docker exec survey_db pg_dump -U $DB_USER $DB_NAME > backup.sql`.
2. Прогоните аудит и почистите «грязные» значения:

   ```sql
   -- даты формата dd.mm.yyyy
   SELECT id, date FROM shifts WHERE date !~ '^\d{2}\.\d{2}\.\d{4}$';
   SELECT id, date FROM pairs  WHERE date !~ '^\d{2}\.\d{2}\.\d{4}$';
   SELECT id, survey_date FROM answers
     WHERE survey_date IS NOT NULL AND survey_date <> '' AND survey_date !~ '^\d{2}\.\d{2}\.\d{4}$';
   SELECT id, moved_at FROM instrument_moves
     WHERE moved_at !~ '^\d{2}\.\d{2}\.\d{4} \d{2}:\d{2}:\d{2}$';
   ```

3. Остановите бота, примените миграцию (`make migrate`), выкатите соответствующий код, запустите бота, проверьте сценарии.
4. Откат при проблемах: `make migrate-down` (миграция конвертирует данные обратно) либо восстановление из дампа.
